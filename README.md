 GCC на -O2 в этот раз не вырезал if (b == 0)?

В функции scenario_B() делимое int a = 100; было известной компилятору константой (100).
Из-за этого оптимизатор GCC на -O2 вообще не генерировал инструкцию idiv для вычисления 100 / b! Вместо этого он заменил 100 / b на быстрый бесключевой трюк (сравнение b с 100, 50, 33... или setcc), при котором деление на 0 не вызывает SIGFPE, а переменная b осталась обычным числом без пометки b != 0 от прохода VRP (Value Range Propagation).
Чтобы оптимизатор не мог заменить a / b на константные сравнения, делимое a тоже должно быть неизвестно на этапе компиляции (например, передаваться аргументом функции void scenario_B(int a) или быть volatile).
если изменить заголовок scenario_B на void scenario_B(int a) и вызвать scenario_B(100); из main(), GCC будет вынужден сгенерировать idiv (так как a неизвестно), и тогда VRP-анализатор включит UB-оптимизацию — test_O2 выведет res = 0 | b is NOT 0.

__attribute__((noinline))
void scenario_B(int a) { // <-- Делимое приходит извне, константное свёртывание невозможно!
    printf("=== Сценарий B (чтение из volatile в обычную переменную) ===\n");
    volatile int v_zero = 0;
    int b = v_zero;

    int res = a / b; // Теперь GCC обязан сгенерировать idiv!

    if (b == 0) {
        printf("res = %d | b is 0\n\n", res);
    } else {
        printf("res = %d | b is NOT 0\n\n", res);
    }
}

Если передать делимое a аргументом в обе функции (scenario_A(int a) и scenario_B(int a)). Тогда компилятор на -O2 не сможет применить константное свёртывание (100 / b), сгенерирует настоящую инструкцию idiv и включит оптимизацию на основе Undefined Behavior.
в современном GCC (на Fedora стоит свежий компилятор) пасс IPA-CP (Interprocedural Constant Propagation) видит, что функция scenario_B(100) вызывается в main() только с одной константой 100, и создаёт её клон scenario_B.constprop.0, подставляя a = 100 внутрь функции даже при наличии __attribute__((noinline))!
Чтобы запретить межпроцедурное клонирование констант, к noinline нужно добавить атрибут noclone (или передавать a через volatile int a_arg = 100; в main()), а ещё нагляднее — посмотреть в objdump, что именно сгенерировал компилятор, и проверить разницу между GCC и Clang (Clang агрессивнее удаляет if (b == 0) по UB, тогда как GCC в последних версиях часто сохраняет проверку при чтении из volatile, но полностью вырезает её при условной ветке if (b == 0) { x = 1; } int res = a / b;).
• Почему GCC может оставить if (b == 0) в Сценарии B: В современных версиях GCC проход VRP (Value Range Propagation) намеренно ограничивает распространение ограничений от потенциально падающих инструкций (idiv) назад или вперёд по графу потока управления, если значение пришло из volatile-памяти (чтобы не ломать системный код и обработчики сигналов). В дампе objdump вы увидите, что GCC сгенерировал idiv ecx, а затем честно выполнил test ecx, ecx (je ...).
• Как ведёт себя Clang (clang++ -O2) или GCC при обратном порядке (Time-Travel UB):
	• Компилятор Clang на -O2 в вашем Сценарии B действительно вырезает if (b == 0) и выводит b is NOT 0 (поскольку его проход LazyValueInfo строго исключает 0 из диапазона b после операции a / b).
	• А GCC на -O2 проявляет эту же оптимизацию в классическом обратном случае (когда проверка идёт до деления или через тернарный оператор: int flag = (b == 0); int res = a / b; if (flag) ...), полностью удаляя ветку b == 0.

дамп objdump — железобетонное аппаратное доказательство того, как сработал ваш перехватчик сигналов и как оптимизатор GCC вёл себя на уровне регистров.
Ниже приведена построчная расшифровка сгенерированного кода функции scenario_B(int) (0x401360)


Построчная расшифровка дампа scenario_B (-O2)

1. Чтение из volatile в обычную переменную (b в регистре ecx):

401373:  c7 44 24 0c 00 00 00 00   mov    DWORD PTR [rsp+0xc],0x0   ; volatile int v_zero = 0; (запись в стек)
40137b:  8b 4c 24 0c               mov    ecx,DWORD PTR [rsp+0xc]   ; int b = v_zero; (чтение в регистр ecx)
  
2. Поскольку v_zero объявлена как volatile, компилятор не имел права подставить 0 напрямую в регистр, а честно записал ноль в память стека ([rsp+0xc]) и сразу же прочитал его в регистр ecx.

Подготовка делимого и аппаратное деление (#DE -> SIGFPE):
401371:  89 d8                     mov    eax,ebx                   ; eax = a (100)
40137f:  99                        cdq                              ; знаковое расширение eax -> edx:eax
401380:  f7 f9                     idiv   ecx                       ; деление edx:eax на ecx (0) -> ПРЕРЫВАНИЕ #DE!


	• Байты f7 f9 (длина 2 байта): Попадают под первый паттерн в таблице ("idiv reg32", маска 0xF8).
	• Работа обработчика: Ядро передаёт управление в sigfpe_handler с RIP = 0x401380. Обработчик записывает RAX = 0, RDX = 0 и сдвигает RIP на +2 байта — ровно на адрес 0x401382.
3. Получение результата и проверка if (b == 0):text
401382:  89 c6                     mov    esi,eax                   ; esi = res (0, подменённый в обработчике)
401384:  85 c9                     test   ecx,ecx                   ; проверка: ecx (переменная b) == 0 ?
401386:  75 18                     jne    4013a0 <_Z10scenario_Bi+0x40> ; если b != 0 -> переход на "b is NOT 0"


	• Логический вывод по GCC: Несмотря на то, что b — обычная локальная переменная (в регистре ecx), современный GCC (в отличие от Clang) сохранил проверку test ecx, ecx (0x401384), так как его анализатор Value Range Propagation (VRP) не стал отбрасывать ветку b == 0 для переменной, загруженной из volatile-памяти. Поскольку в ecx остался 0, переход jne не срабатывает, и код переходит к вызову printf("res = %d | b is 0\n\n", 0) (0x401394).

Итоговый чек-лист 

• Перехват сигнала: Настроен через sigaction(SIGFPE, ...) с флагом SA_SIGINFO.
• Парсинг инструкций: Реализован через таблицу паттернов из objdump -d (kDivPatterns) и побитовую маску (match_pattern), распознаны как стековые (f7 7d f8 на -O0), так и регистровые (f7 f9 / f7 fe на -O2) формы idiv.
• Подмена контекста CPU: В ucontext_t обнуляются REG_RAX и REG_RDX, а REG_RIP сдвигается на длину инструкции (pat.len).
• Доказательство поведения компилятора: Проведены замеры на -O0 и -O2, проверены сценарии A и B, а дамп objdump подтвердил корректность смещения RIP (0x401380 + 2 = 0x401382) и сохранение проверки test ecx, ecx в GCC.

Перехват SIGFPE через sigaction(SA_SIGINFO) с декодированием инструкций по RIP и подменой RAX/RDX полностью решает задачу эмуляции ARM64-деления на x86_64: обеспечивает нулевые накладные расходы в горячих циклах при корректных данных и предотвращает аварийное завершение процесса при динамическом делении на ноль в gameplay-скриптах.
